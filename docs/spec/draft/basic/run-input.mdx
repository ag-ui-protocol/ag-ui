<DraftNotice />

Events flow from producer to consumer. Exactly one message flows the other way:
`RunAgentInput`, sent once to open each exchange. Everything the producer knows
about the conversation arrives through it. The run it requests is the exchange's
last; a stream that replays a thread's history carries the earlier runs
[without further input](/spec/draft/basic/transports#the-binding-contract).

The [schema](/spec/draft/schema#runagentinput) defines its shape; this page states what
each field obliges. A producer MAY echo the input back on `RUN_STARTED.input`,
so a consumer that did not make the request can still see what the agent was
asked.

## Identity

`threadId` names the conversation and `runId` names the run this input
requests; both are REQUIRED. Every run on the stream carries the input's
`threadId` on its boundary events — `RUN_STARTED` and `RUN_FINISHED`, the two
that carry identity — and each run's two boundary events MUST agree on their
`runId`. The requested run echoes this input's `runId`; a replayed run
carries its own. `parentRunId` is OPTIONAL and names the run that spawned
this one, when an agent starts another agent as a separate run.

## `protocolVersion`

OPTIONAL in the schema, because absence identifies a peer from before the
protocol carried a version — but a consumer implementing this version MUST
declare the version it speaks here, unless it knows its peer predates the
field and omits the member rather than risk an old parser rejecting it. The
producer answers with its own declaration on `RUN_STARTED`; the rules are in
[Versioning](/spec/draft/basic/versioning#version-negotiation).

## `messages`

REQUIRED. The conversation so far, in order. A producer MUST treat it as the
complete history it is being shown, unless the producer declares
[server-managed history](#server-managed-history). Outside that mode the
protocol has no side channel through which earlier turns arrive.

The message types and their content shapes — including multimodal
[`ContentPart`](/spec/draft/schema#contentpart)s carrying text, images, audio,
video and documents by URL, as inline data or as a
[provider file handle](#provider-file-handles), on user messages and on the tool
messages that answer [frontend tool calls](/spec/draft/events/tool-calls#frontend-tools) —
are the schema's business. Two behavioural rules attach:

- A producer that cannot use a content part — a model without vision handed an
  image — MUST NOT fail the run because of it. Skipping what it cannot use and
  continuing is the conforming behaviour; losing content on a downgraded
  *outgoing* path is different and obliges a warning
  ([Versioning](/spec/draft/basic/versioning)).
- Activity messages never travel back to the producer: a consumer MUST strip
  them from `messages` before sending. They are the consumer's rendering
  material, not conversation the agent resumes from.

### Server-managed history

<Since version="1.1" />

Some producers keep each thread's history in a store of their own. They may
need it for persistence or audit, they may be unable to accept requests whose
size grows with the conversation, or they may refuse to let the consumer
rewrite earlier turns: history the consumer sends is input like any other,
and an assistant or system message the producer never wrote is a way to
inject instructions into the model's context. Such a producer declares
`state.serverManagedHistory: true` in its
[capabilities](/spec/draft/basic/capabilities#server-managed-history), and
`messages` then carries only what the producer has not yet seen.

A consumer reads the declaration from `state.serverManagedHistory`. Because
SDKs generated from 1.0 cannot express that field, a producer MAY also
declare it as `custom.serverManagedHistory: true`, and a consumer SHOULD
treat either as the declaration.

**Confirmed messages.** A consumer tracks which messages the producer holds.
When a run ends with `RUN_FINISHED`, whatever its outcome, the messages that
run's input carried and the messages its events created are *confirmed*.
Every message a `MESSAGES_SNAPSHOT` carries is confirmed when the snapshot
arrives. A run that ends with `RUN_ERROR`, or is
[truncated](/spec/draft/basic/transports#truncation), confirms nothing, and a
message the consumer adds while a run is in progress is not confirmed by
that run.

**The cursor.** The cursor is the id of the latest confirmed message, in the
consumer's order, that the producer is expected to hold: a message the
producer created through its events or a snapshot, or a `user` or `tool`
message the consumer sent. Activity and reasoning messages never serve as
the cursor, and neither does an `assistant`, `system` or `developer` message
the consumer authored, since the producer does not store those.

**The consumer.** A consumer MUST NOT use this mode with a producer that has
not declared the capability: such a producer treats `messages` as the
complete history, and a partial list would silently lose the conversation.
With a producer that has declared it, a consumer MAY send the complete
history as usual, or MAY send only what is new. A consumer that sends only
what is new:

- MUST send in `messages` every unconfirmed message, in order, with activity
  messages still stripped. The list MAY be empty, as for a run that only
  carries [`resume`](#resume) entries.
- MUST also send, for every `tool` message in the list, the `assistant`
  message carrying the tool call it answers, even when that message is
  confirmed. A tool result is meaningless without the call it answers, and
  the call tells the producer which tool the result belongs to. In the
  consumer's order the call and its results precede any later `user`
  message.
- MUST send every `system` and `developer` message on every run, confirmed
  or not. They are the application's instructions for the run, not turns of
  the conversation, and the producer does not store them.
- MUST NOT send any other confirmed message.
- MUST set the [reserved key](#reserved-keys) `ag-ui:historyCursor` in
  `forwardedProps` to the cursor, and MUST omit the key when there is no
  cursor. A consumer whose `forwardedProps` is not an object cannot carry the
  cursor and MUST send the complete history instead.
- MUST send the complete history, and MUST omit the cursor, for a run that
  follows a divergence: a confirmed message that has since been removed from
  the consumer's list, or whose content has changed, as when the user edits
  an earlier turn, rewinds the conversation or regenerates an answer. The
  producer still holds what was confirmed, and a delta cannot express a
  removal or a change; the complete history without a cursor hands the
  decision to the producer, as [below](#resending-the-complete-history).

**The producer.** A producer that declares the capability:

- MUST build the model's context from its own store for the thread, not from
  `messages`, together with whatever `system` and `developer` messages of
  the input its policy admits.
- MUST store every message its events create in a run that ends with
  `RUN_FINISHED`, under the `id` the events carried, and every message it
  accepts from the input under the `id` the input carried. A message the
  consumer was shown under one id and the store holds under another breaks
  the cursor.
- MUST treat each incoming message as a candidate to append to that store. A
  message whose `id` the store already holds MUST be ignored; it never
  replaces the stored message, unless the producer imports a resent history
  as [described below](#resending-the-complete-history). A consumer that
  sends the complete history therefore adds only what is new. This includes the `assistant` message
  sent alongside a tool result: when its `id` is known the producer MUST NOT
  treat it as new content and MUST NOT prefer its content over the store,
  though it MAY read it to find the name of the tool the result answers.
- SHOULD accept only `user` messages, and `tool` messages that answer a tool
  call the store records as unanswered. It SHOULD drop every other message,
  including `assistant` messages it does not hold and `tool` messages that
  answer no pending call. Dropping a message is not an error: the run
  proceeds without it.
- MAY use the input's `system` and `developer` messages for the run, by its
  own policy, and MUST NOT store them in the thread's history as turns the
  consumer wrote. The consumer resends them on every run, so the current
  ones are always at hand.
- MUST build any `MESSAGES_SNAPSHOT` it emits from its store. A snapshot
  replaces the consumer's list and confirms every message in it, so one built
  from the input would confirm what the store does not hold. A producer MAY
  emit one so the consumer's list matches the store again, for example after
  dropping a message. Such a snapshot omits the consumer's `system` and
  `developer` messages, which the producer does not store, and the producer
  is not required to echo them. A consumer using this mode MUST therefore
  keep its own `system` and `developer` messages that a snapshot omits, as it
  keeps activity and reasoning messages under the
  [snapshot reconciliation](/spec/draft/events/state#messages_snapshot)
  rules, so that it can keep sending them on every run.
- MUST check a cursor when the input carries one, before it emits any event
  other than `RUN_STARTED` and before it calls the model. If it does not know
  the thread, or its store for the thread holds no message with the cursor's
  id, it MUST end the run with `RUN_ERROR` carrying
  `code: "HISTORY_UNAVAILABLE"`, and the only event that MAY precede that
  `RUN_ERROR` in the run is `RUN_STARTED`. A producer MUST NOT use the code
  for any other failure. An input with no cursor is not checked: it opens a
  thread, or resends the complete history. A cursor that names a stored
  message older than the store's latest is not an error either: the store is
  authoritative, and the producer MAY emit a `MESSAGES_SNAPSHOT` to bring the
  consumer up to date.

**Recovery.** A consumer that sent a cursor and receives `RUN_ERROR` with
`code: "HISTORY_UNAVAILABLE"` before any event other than `RUN_STARTED`
SHOULD forget which messages are confirmed and retry once, sending the
complete history and no cursor. The refused run produced nothing, so the
retry MAY reuse its `runId`. It MUST NOT retry a second time: a
second `HISTORY_UNAVAILABLE` is surfaced as any other failed run is. A
`RUN_ERROR` that arrives after any other event is an ordinary failure,
whatever its `code`, and is never retried.

**Order.** The producer's store defines the order of the thread's messages.
A message the consumer added while a run was streaming is sent in the next
run's delta and stored after that run's output, even when the consumer's
list shows it earlier; a later `MESSAGES_SNAPSHOT` is authoritative for the
order, and a consumer MUST NOT treat the resulting reordering as a
divergence.

#### Resending the complete history

An input without a cursor carries the complete history: the consumer is
opening a thread, does not use the mode, is recovering from
`HISTORY_UNAVAILABLE`, or has diverged from what it confirmed. When the
producer holds the thread and the resent history agrees with its store, the
rules above already decide the run: known messages are ignored and the new
ones are candidates as usual.

When the producer does not hold the thread, or the resent history does not
agree with its store (it lacks a stored message, or carries a stored `id`
with different content), the acceptance rule alone does not decide what the
thread becomes, since it would keep only the new user turns. That is the
producer's policy. It MAY import the resent history as the thread's history,
replacing what it stored, knowing the history is consumer-supplied and
carries no more trust than any other input. It MAY instead start the thread
afresh, storing only the messages the acceptance rule admits. A producer
that holds the thread and does neither keeps its store, which the rules
above make authoritative, and SHOULD emit a `MESSAGES_SNAPSHOT` so the consumer's list
matches it again. How a producer detects the disagreement is its own
business; one that cannot tell keeps its store.

### Provider file handles

A media part's `source` says where its bytes are: carried inline (`data`),
fetchable by URL (`url`), or already at the model provider under a handle the
provider issued (`file`) — an OpenAI or Anthropic file id, a Gemini file URI,
a storage URL only that provider can read. The
[`file` source](/spec/draft/schema#filesource) exists because a handle is
neither of the other two things: it carries no bytes, and it is not fetchable
by anyone but the provider that minted it, so putting it in `url` invites every
other peer to try.

- A `file` source's `value` is opaque. A peer MUST NOT fetch it, parse it or
  read a scheme out of it; it hands the handle to the provider, or it does not
  use the part.
- `provider` names who issued the handle, when the producer knows. It is
  OPTIONAL — an agent already knows which provider it talks to — and when
  present SHOULD be the lowercase vendor id that
  [`TokenUsage.provider`](/spec/draft/schema#tokenusage) uses, so a peer can
  tell before sending whether a handle is one it can use.
- A producer handed a handle it cannot resolve — another provider's, an
  unknown provider's, one that has expired — is in the situation the first
  rule above already covers: it MUST NOT fail the run, it skips the part and
  continues, and it SHOULD say so. A handle's lifetime is the provider's
  business; a producer that wants to carry an expiry does so in the part's
  `metadata`.
- The source arms are a closed set: a source whose `type` a peer does not
  recognise fails validation rather than being carried through. That is why
  this arm is in 1.0 and not a later minor version — a consumer built to 1.0
  could never have passed it on.

## `tools`

OPTIONAL. The application's own tools — *frontend tools* — offered to the
agent for this run: name, description and, where the tool takes arguments, a
parameter schema. The
application executes them, not the agent; calling one hands control back
across the run boundary, the round-trip
[Tool calls](/spec/draft/events/tool-calls#frontend-tools) specifies.

An absent list and an empty list mean the same thing: no tools. A producer
MUST treat a missing `tools` exactly as it would treat an empty one, and a
consumer MAY omit an empty list rather than sending `[]`.

## `context`

OPTIONAL. Information the application wants in the agent's context, as
description–value pairs. It exists to be *injected*: a producer SHOULD make
every entry available to the model as part of the run's grounding. How — a
system prompt, a preamble, whatever the framework does with context — is the
producer's business; the protocol says only that context is for the model to
see, not bookkeeping for the transport.

Absence means the same as emptiness, exactly as for `tools`.

## `state`

OPTIONAL. The state the run starts from — the consumer's last agreed value,
typically what the previous run's [state events](/spec/draft/events/state)
left behind. An absent `state` means the empty object: nothing has been
agreed, and `{}` is nothing. A producer that emits state deltas MUST compute
them against this value until its own first snapshot replaces it.

## `forwardedProps`

OPTIONAL. An application-specific channel passed through to the agent untouched.
Any JSON value except a whole `null`, which means the field is omitted. Null
values inside the payload are preserved. The protocol attaches no meaning to the
payload beyond its [reserved keys](#reserved-keys), and intermediaries MUST NOT
alter it.

### Reserved keys

<Since version="1.1" />

When `forwardedProps` is an object, keys beginning with `ag-ui:` are reserved
for the protocol's own use, as the `ag-ui` key is in
[metadata](/spec/draft/basic/metadata#keys). An application SHOULD NOT invent
keys with that prefix, and a producer MUST ignore a reserved key it does not
recognise. An application that already used such a key under 1.0 keeps
working with a producer that does not declare the feature the key belongs
to; with one that does, the key means what this section says. This version defines one:

| Key                   | Value                                                     | Specified in                                        |
| --------------------- | --------------------------------------------------------- | --------------------------------------------------- |
| `ag-ui:historyCursor` | The id of the latest confirmed message the producer holds | [Server-managed history](#server-managed-history)   |

## `resume`

OPTIONAL. Answers to the interrupts that ended a previous run, when this run
continues from one. The entries and their obligations are specified in
[Interrupts and Resume](/spec/draft/basic/patterns/interrupt-resume).

## Error Handling

An input a producer cannot parse, or that is malformed — a known field
carrying a value the schema rejects — is rejected before `RUN_STARTED`,
through the transport's error path: the run never starts, and no stream
exists for a `RUN_ERROR` to travel on. How the rejection is delivered is each
[transport binding](/spec/draft/basic/transports)'s business.

Unrecognised members of the input are not malformed. The
[processing model](/spec/draft/basic/processing)'s asymmetry binds this
direction too: a producer meeting input material it does not recognise strips
it with a warning and runs, so a newer consumer's input does not bounce off
an older producer.
